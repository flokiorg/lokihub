Release candidate for 0.5.0, covering everything merged to `main` since 0.5.0-rc.7. This one comes out of a security audit of the Cash Hub and its new private transport, so it is mostly correctness and disclosure fixes — several of them breaking for clients.

## Breaking
- The four bill methods — `cash_status`, `cash_redeem`, `cash_transfer`, `cash_consolidate` — are served over the private transport only, and refused on the standard NIP-47 connection. A standard-transport request p-tags the bill's own wallet pubkey, so a holder's bills were a public, linkable set however well the payload was encrypted; consolidating fifty bills published fifty requests resolving to one. The refusal names the transport and the kinds to use rather than reading as an unknown method. (#111)
- `list_recipients` is gone; `cash_status` is the one name, in the dispatcher, the permission scopes and `get_info`. (#111)
- `get_info` reports the bill methods under a new `private_methods` field. `methods` means "callable here", and these are not — so a client could previously only learn they exist by hardcoding the list. Presence here is informational and never permission. (#111)
- `mint_cash` accepts an optional `idempotency_key`. A caller that retried after a timeout previously minted and funded a second wallet. A repeat is refused rather than replayed, because a cash-mode secret exists only in the reply the caller missed; a failed mint releases its key. (#111)

## Operators: your node must be able to sign for the hub

The hub announces its private-transport inbox in an event signed by the node's own identity key, because that key is the only thing a client can anchor trust to. lokihub asks the node for that signature over gRPC (`signrpc.SignMessage` with a Schnorr signature over the node key family), so **the connected flnd must expose `signrpc` and its macaroon must permit signing.**

If it cannot, startup logs `announcement failed, private transport is unreachable to new clients` and carries on. Existing clients that already know the inbox key keep working; **clients that have never talked to this hub cannot reach it at all** — and since the bill methods are now served over the private transport only, that means they cannot use bills. Check for that line after upgrading. No new flnd version is required: this uses the standard signer RPC, and `flnd v0.2.2-beta` is enough. (#111)

## Money safety
- A redemption that would pay out nothing is refused instead of performed. The redeem fee saturates at the amount it is charged on, so a slice at or below the flat fee base quoted a payout of zero — and an amountless invoice matched that, so the exact-match check passed. The slice was consumed, no payment was made, and the response said success. (#111)
- A redeem fee now has a flat base as well as a proportional part, with the route reserve capped so payout plus reserve equals the slice. The hub could previously pay up to 10,000 mloki in routing to earn 1, on a route the holder chose. (#111)
- Converting a bill to cash mode after it has changed hands splits instead of reassigning in place, so a previous holder can no longer recover a bill they already sold. An in-place reassignment writes no archive record, which made a bill that had changed hands indistinguishable from one that never had. (#111)
- An amountless same-node redemption no longer settles for zero while debiting the full amount. (#111)
- A bill is never minted without a reachable relay hint. A bill is reachable only through the hints inside its own token, so one minted without any holds value its holder can never reach — and a hub with no relay configured was minting with a single empty hint, which every existing guard accepted. (#111)
- A Cash Hub's expiry ceiling can be "never". (#111)
- `create_cash_hub` validates `min_transfer_mloki` and `redeem_fee_base_mloki`, which only the update path checked before, so create accepted configurations update would reject. (#111)

## Disclosure
- `cash_status` no longer answers a caller holding no slice. On a bill carrying any `connection_key` recipient, possession of the token alone read the whole roster — every recipient's identity value, entitled amount and claimed state. The parties who hold a token but no slice are real: a removed recipient, one who transferred their slice away, and anyone the connection was ever shown to. (#111)
- A `connection_key` recipient can read their own row again, via the Identity Authority attestation `cash_redeem` already requires. Their identity value is a hash, so there was nothing for the roster filter to match on. (#111)
- `cash_status` honours its scope, and co-recipients are no longer disclosed by default. (#111)
- Circle join details are nested so co-members cannot read them, `sign_message` refuses mint-provenance payloads, and a read-only token can no longer read the swap seed. (#111)
- An unknown bill, an unverifiable proof and an unserved method are all answered by the same silence, and a bill proof is checked before the bill is looked up so a miss costs what a hit costs. (#111)

## Fixed
- A proof can no longer be lifted out of its envelope and replayed in another: a nonce stays burnt as long as a proof bound to it can still verify, where a lapsed entry used to be refreshed and re-admitted. (#111)
- An oversize reply is detected wherever it falls in the batch, not only when it happens to come first. The same results in a different order published a first chunk promising a second that could never be encoded, leaving the client waiting out a reply that would never arrive. (#111)
- One envelope can no longer burn a shared bill's whole hourly claim budget, nor spend it on items that failed validation. (#111)
- A lapsed invoice no longer pins its wallet, hub and identity forever, and invoices on hold are counted. (#111)
- Both compensating rollbacks check the wallet is actually empty before deleting it, rather than trusting that the reversal call returned without error. (#111)
- A bill reassigned from cash to an identity no longer keeps a stale "identity required" hint that made it unreceivable by its rightful holder. (#111)
- An Identity Authority attestation is verified once per request instead of once per claim, so a bill with many recipients no longer costs a verification each. (#111)
- `db_migrate` copies all 27 tables. It copied six and reported success: the schema check only asserts a table exists, and the rest were created empty at the destination — so transactions migrated while the claims that record who owns what did not, and money arrived with nobody holding a claim to it. (#111)
